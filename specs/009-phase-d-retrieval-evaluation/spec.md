**Feature Branch**: `009-phase-d-retrieval-evaluation`

## Scope and objective

Deliver a native-Windows, reproducible retrieval evaluation harness and report, and create, validate, protect for independent ChatGPT source-based review, freeze, and evaluate Golden v1. The Person 2 approved target is nine questions across five types and four functionality tags. Person 2-owned policy adopts AI generation/assistance with transparent provenance and mandatory independent ChatGPT scientific review; after the review gate the user separately authorizes continuation. ChatGPT review is not human verification. Preserve the prior human-authorship rule in decision history. The repository constitution and shared `docs/EVALUATION_PLAN.md` remain unchanged; the resulting artifact is a Person 2 evaluation dataset, not a shared human-verified release unless broader governance is later amended. Keep v0 and Phase A/B/C behavior unchanged. A separately versioned functionality sidecar is internal to Person 2; integration proposals are handed off without changing shared contracts. P2 retrieval metrics do not score generated-answer quality.

### User Story 1 - Validate and match approved evidence (Priority: P1)

As the retrieval owner, I need versioned Golden records matched to retrieved chunks by stable source evidence, so that quality metrics measure retrieval against ground truth rather than generated chunk IDs.

**Independent Test**: Synthetic versioned fixtures prove partition isolation, schema/version/hash checks, DOI and locator normalization, exact matching, controlled fallback behavior, and malformed-input rejection without loading real held-out content.

**Acceptance Scenarios**:

1. Given a frozen dataset and explicit question-ID allowlist, when the loader runs, then only allowlisted question objects are buffered and decoded and all IDs must match the declared partition exactly.
2. Given a positive evidence reference, when a returned chunk is matched, then exact normalized DOI plus source locator is primary; the only fallback is matching DOI, labeled section, and exact quotation containment as specified in the protocol.
3. Given duplicate results or multiple distinct references, when matching occurs, then each unique evidence unit is counted once and distinct references remain distinct.

### User Story 2 - Compare retrieval modes with fixed metrics (Priority: P1)

As a retrieval owner, I need comparable dense, lexical, and hybrid measurements on the same frozen cases, so I can report observed retrieval behavior without tuning against held-out data.

**Independent Test**: Independent metric oracles cover cutoffs, multiple references, no-result cases, duplicate hits, deterministic ties, and ineligible negative questions.

**Acceptance Scenarios**:

1. Given identical questions, corpus snapshot, filters, embeddings, matching rules, and candidate ceiling, when each retrieval mode runs, then each produces a separate versioned per-question report and run manifest.
2. Given a question with positive references, when metrics are calculated, then Recall@K, Evidence Hit@K, and applicable MRR use the definitions and denominators in this specification.
3. Given an insufficient-evidence question with no positive evidence references, when positive metrics are calculated, then Recall and MRR are null/not applicable and the negative result is reported separately.

### User Story 3 - Reproduce latency and run provenance (Priority: P1)

As a reviewer, I need the evaluation command, environment, corpus identity, and timing details recorded, so I can reproduce and correctly limit interpretation of the results.

**Independent Test**: Synthetic manifests validate required fields, deterministic serialization, component timing aggregation, repetition statistics, and secret redaction.

**Acceptance Scenarios**:

1. Given a run, when its manifest is written, then it identifies dataset and partition hashes, corpus and delivery identities, code revision, database/migration versions, embedding and retrieval configurations, command, environment, time, failures, and embedding usage/cost.
2. Given repeated measurements, when timing summaries are generated, then warm/cold status, repetition count, median, p95, maximum, and failures are explicit for available stages.
3. Given missing or incompatible cached query embeddings, when a run would require a paid call, then it stops before the call unless a separate explicit authorization and spend cap exist.

### User Story 4 - Create and freeze Golden v1 (Priority: P1)

As the Person 2 evaluation owner, I need AI-generated/AI-assisted v1 candidates with accurate provenance, independent ChatGPT source-based review, source-traceable annotations, protected partitions, and an explicit continuation gate, so Phase D can evaluate beyond the narrow v0 pilot without circular ground truth.

**Independent Test**: Validate synthetic curation records and review manifests, then confirm the real P2 v1 dataset has the approved size, category plan, coverage, source evidence, provenance, ChatGPT per-record review evidence, protected review packet, and frozen partition hashes without running retrieval.

**Acceptance Scenarios**:

1. Given a pre-registered design and partition procedure, when v1 records are drafted, then no retrieval outputs or held-out performance have been observed and every candidate enters the protected ChatGPT review gate before subsequent implementation/evaluation.
2. Given each proposed v1 question, when ChatGPT manually inspects it in a fresh review context, then wording, answerability, expected finding, DOI, source locator, quotation, relevance labels, corpus scope, provenance, functionality annotation, and insufficiency rationale are checked against original source material and review evidence is recorded per record.
3. Given all nine records pass ChatGPT review, when the review report is complete, then all work stops until the user explicitly authorizes continuation; defects require correction and re-review of affected records.
4. Given all records pass review, when the dataset freezes, then v0 remains unchanged, v1 has its own version/hash/history and the approved category/functionality matrix is covered, with stratified dev/held-out ID sets frozen before retrieval tuning or evaluation.

## Requirements

### Functional Requirements

- **FR-001**: The evaluation MUST load only IDs from the approved partition allowlist and MUST NOT decode or retain non-allowlisted question objects. Golden v0's historical full-deserialization exception MUST remain disclosed as a Phase C event; it is not evidence that Phase D accesses held-out data permissively.
- **FR-002**: The harness MUST validate schema, dataset version, corpus version, partition identity, duplicate IDs, and frozen dataset/partition hashes before retrieval.
- **FR-003**: The harness MUST match evidence by normalized DOI and exact source locator. It MAY use only the controlled fallback of matching DOI, labeled section, and exact quotation containment. Section-path-only matches MUST be diagnostics, never positive matches.
- **FR-004**: Relevance labels `2` and `3` MUST count as relevant; labels `0` and `1` MUST not. A distinct labeled DOI+source locator+quotation identity is one evidence unit; repeated retrieval of that same unit counts once.
- **FR-005**: The comparison MUST include exact dense cosine, PostgreSQL lexical FTS, and hybrid RRF using the accepted Phase B implementations. Each arm MUST use the same frozen cases, snapshot, filters, embeddings, evidence matching, candidate ceiling, and cutoffs.
- **FR-006**: The accepted retrieval configuration MUST remain frozen during held-out evaluation: `text-embedding-3-small` at 1536 dimensions, PostgreSQL/pgvector exact vector search, PostgreSQL English FTS, and RRF `k=60`, with no reranker. Any changed retrieval setting creates a separately identified exploratory run and MUST NOT replace the preregistered baseline.
- **FR-007**: At `K ∈ {1,3,5,10,20}`, capped by the valid returned/eligible list, per positive question `Recall@K = distinct relevant evidence units retrieved in top K / total distinct relevant evidence units labeled for that question`.
- **FR-008**: Per positive question `Evidence Hit@K = 1` if at least one relevant evidence unit occurs in top K, otherwise `0`. `MRR@K = 1/rank` for the first relevant result in top K, otherwise `0`, only for positive questions where first-hit ranking is meaningful. Results beyond K do not contribute.
- **FR-009**: For each dataset cohort and retrieval arm, aggregate per-question metrics and macro means over eligible answerable questions; report question-type and functionality-stratified descriptive summaries with n. Recall numerator/denominator are unique relevant gold evidence units within each question; never micro-pool evidence units. Evidence Hit is binary per eligible positive question, and MRR uses that same population. Report answerable and insufficient-evidence populations, eligible/excluded n, every exclusion reason, evidence denominators, nulls, and cohort/dataset/partition provenance separately.
- **FR-010**: Negative questions MUST NOT be counted correct merely because retrieval returned nothing. Any false-support rate requires a frozen, blinded human adjudication of retrieved passages as `supported`, `partial`, `unsupported`, or `uncertain`; its denominator and treatment of uncertain judgments MUST be explicit before evaluation. If this adjudication is unavailable, report retrieval observations only and mark false-support rate NOT COMPUTED.
- **FR-011**: Latency MUST record available stages separately (query embedding, database dense/lexical, fusion/ranking, context selection, total retrieval), cold and warm state, repetition count, median, p95, maximum, and failures. A stage that cannot be isolated MUST be marked unavailable, not inferred.
- **FR-012**: Run manifests MUST include dataset version/hash, cohort/partition name/hash/IDs, corpus version/hash, active import ID, delivery digest, Git revision/dirty state, database and pgvector versions, migration revision, embedding model/dimensions/cache identity and usage/cost, retrieval/filter configuration, K, command, timestamp, Windows build, CPU/memory, Python/dependency lock identity, repetitions, failures, and output hashes. Ordinary manifests/reports MUST exclude secrets and held-out question text; the complete v1 dataset and review packet remain separately protected and version-control-excluded, with evaluation access only through authorized allowlisted IDs.
- **FR-013**: Evaluation database access MUST be read-only, identity-preflighted to exactly `sciscope_test_005` before connection/use, and verify the frozen 17/319/728/728 pilot and corpus identity before and after. No migration, write, schema change, ingestion, or production `sciscope` access is permitted.
- **FR-014**: Golden v0 MUST remain byte-for-byte unchanged. Its 5 development questions are smoke/regression-only; its 16 held-out questions are reported only after explicit held-out evaluation authorization and all data gates.
- **FR-015**: Golden v0 has 21 AI-drafted questions across 12 papers with existing records describing Person 1 verification. The five previously exposed development questions are smoke/debug only; the remaining 16 are a separate protected cohort. Preserve the documented Phase C full-file deserialization exception but do not infer unseen status from it; audit exposure/provenance when evaluation access is authorized. v0 results are a limited pilot cohort, not a broad/general estimate. No Person 1 confirmation is a P2 approval dependency.

- **FR-026**: After explicit authorization for the named protected cohort, query-vector preflight MUST bind question ID to retrieval-normalized text (`str.strip()` only) hash, final prefixed input hash, dataset version/full hash, cohort/partition hash, corpus and active embedding-set identity, provider/model response identifier, dimensions, prefixes, cache key/provenance, vector bytes, and frozen config. Require provider `openai`, model `text-embedding-3-small`, 1536 dimensions, empty query/passage prefixes and compatible `float32-le` corpus. Validate finite vector components, nonzero norm, expected L2 tolerance, checksums, and cache-file/manifest integrity. Existing passage-cache entries do not alone establish query provenance. Missing, stale, mismatched, corrupt, or unverifiable vectors fail closed; no silent substitute, regeneration, removal, or denominator change.
- **FR-027**: A gold evidence unit MUST be a canonical unique annotation identity bound to normalized DOI, exact canonical durable locator, and exact quotation UTF-8 content hash when present (otherwise DOI+locator); identical annotations are deduplicated before denominator calculation. Duplicate canonical units with conflicting labels MUST fail validation for curator resolution. A retrieved chunk may satisfy multiple distinct gold units only if it independently matches each unit's DOI and locator or allowed quotation fallback. Multiple returned chunks matching the same gold unit count that unit once, at its earliest ranked match. Duplicate/overlapping chunks MUST NOT increase the hit numerator or denominator; distinct source passages remain distinct units.
- **FR-028**: Per-question Recall@K MUST be the number of distinct matched relevant gold units among top K divided by the total distinct labeled relevant gold units and MUST be clamped by set semantics to [0,1]; duplicates cannot inflate it. Evidence Hit@K is 1 iff that numerator is nonzero. MRR@K uses the earliest rank at which any positive unit is matched, counting a gold unit only once; undefined/not-applicable cases remain null and are excluded from the eligible macro denominator with reason. One retrieved chunk matching multiple different relevant source units may credit each once only where each annotation is independently supported by the chunk's locators/content.
- **FR-029**: Metric unit and mapping policy MUST be tested with independent synthetic oracles for one-to-many and many-to-one matching, duplicate/overlapping chunks, repeated locators, same-locator quotations, DOI normalization, fallback boundaries, repeated retrievals, no positive references, and K beyond available results. Oracle cases MUST assert Recall never exceeds 1 and duplicate results never improve Recall/Hit/MRR.

### Non-goals

- Changing schemas, migrations, the frozen pilot, Phase A/B/C code or evidence, embedding model, retrieval algorithms, shared contracts, public facade, or production configuration.
- Answer-generation quality, refusal behavior, citations emitted by an LLM, frontend/API integration, or cross-owner shared-contract adoption (Phase E / other owners).
- Tuning on held-out results, new reranker experiments, paid API calls by default, or substituting unverified Golden data.
- Claims of statistical significance or general performance from the small pilot set.

### Key entities

- **Frozen partition**: Versioned dataset hash plus immutable named ID set and purpose (development or held-out).
- **Evidence unit**: A distinct human-labeled DOI/source-locator/quotation reference, independent of derived `chunk_id`.
- **Evaluation run**: One frozen retrieval arm with manifest, per-question outcomes, aggregate report, and artifact hashes.
- **Negative adjudication**: Human review label for retrieved evidence on a question expected to be insufficient.
